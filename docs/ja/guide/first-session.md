# 最初のセッション

> この文書は[英語版](../../guide/first-session.md)の翻訳です。食い違う場合は英語版が正です。

このページでは 1 つのプロジェクトを通して、モデルを頼む、結果を読む、変更する、2 つの版を比べる、
自分のデータを持ち込む、までを体験します。studio が起動していることが前提です
([はじめに](getting-started.md))。

## 1. 小さなことを頼む

空のプロジェクトでは、チャットに 3 つの例文が表示されます。クリックするとメッセージ欄に入ります。
どの言語で書いても構いません。エージェントはあなたの言語で答えます。例えば:

> 15 都市を回る最短の巡回路を求めて

**Enter** で送信します(**Shift+Enter** で改行)。日本語入力の変換を確定する Enter では送信されません。

## 2. エージェントの作業を見る

エージェントが作業している間、**Send** ボタンは **Stop** に変わり、チャットには ▸ で始まる灰色の行で
各ステップが表示されます。例えば:

```
▸ read_docs problems         optopus のドキュメントを読む
▸ api_help Tsp               コンストラクタを正確に調べる
▸ write_file model.py        プロジェクトのファイルを 1 つ書く
▸ check_model                モデルを組み立て、各ヒューリスティックを最大 2 秒試す
▸ run_solver                 求解し、リビジョンを作る
```

モデルが変わるような不明点があると、エージェントは推測せずに短い質問を 1 つします。チャットで答えて
ください。データを渡さなければ、小さなインスタンスを自分で作り、そう伝えます。

最初のモデルはたいてい 1〜2 分かかります。求解そのものは、長くと頼まない限り 10 秒程度に抑えられます。
**Stop** でエージェントを中断できます。それまでに書いたものは残ります。

## 3. 結果を読む

`run_solver` が終わると、キャンバスの **Result** タブにリビジョン 1 が表示されます。

- **ビュー**: エージェントがこの問題のために書いた表示。この例では巡回路の地図と主要な数値(経路長)。
  スケジュールならガントチャート、選択なら表、といった具合です。
- **Convergence**(収束): その時点までの最良目的関数値を時間(グラフ上の切り替えで反復回数)に対して
  描いたもの。ラン 1 回につき 1 本の曲線です。終わりでもまだ改善している曲線は、もっと探索すれば
  良くなることを示します。
- **Heuristic**: どう探索したか。`SimulatedAnnealing` などの手法とパラメータ、停止条件、シード、
  ラン数。

エージェントの返信は結果を数行でまとめ、次に変えられることを提案します。**Model** タブには元になった
ファイルが、**Runs** タブには全ランの表(最良値、初期値、反復回数、時間)があります。画面の各部分は
[画面の説明](interface.md)を参照してください。

## 4. 変更を頼む

課題・データ・探索について、普通の言葉で何でも頼めます。

> 30 都市にして、訪問順を表で見せて

> 1 ランあたり 5 秒、5 ラン回して

エージェントは頼まれたことに必要な部分だけを変えて解き直し、リビジョン 2 ができます。求解はすべて
残っていて、キャンバス上部の **Revision** メニューからどれにでも戻って表示できます。

## 5. 2 つのリビジョンを比べる

**Compare** を開くと、2 つのリビジョンが並びます。最良目的関数値の変化(良くなったか、悪くなったか、同じか)、
両者の主要な数値、それぞれの最良ランの収束、ファイルの差分です。上部の 2 つのメニューで別の
リビジョンを選べます。

## 6. ヒューリスティックを比べる

どの探索手法がこの問題に向いているか知りたいときは、こう頼みます。

> 焼きなまし法、タブーサーチ、Late Acceptance Hill Climbing をそれぞれ 5 ランずつ比べて

同じシードで実行されるので、どれも同じ解から始まります。Convergence のグラフに重ねて表示され、
**Runs** にはヒューリスティックごとの最良・平均・最悪の結果と時間の表が加わります。

## 7. 自分のデータを使う

メッセージ欄の横の **+** をクリックしてファイルを選びます。CSV、TSV、`.txt`、Excel(`.xlsx`)、
JSON に対応し、1 ファイル 20 MiB までです。ファイルは欄の上にチップとして表示されます。何のデータかを
書いて送信してください。

> これは配送先の住所と需要です。容量 100 のトラック 3 台で回るルートを作って

エージェントは列と先頭の行を確認し、列の意味や単位が分からなければ質問し、行をプロジェクトの
`instance.json` に取り込みます。以降そのデータはすべてのリビジョンの一部になるので、元のファイルが
変わっても古いリビジョンは同じように解けます
([ADR 0004](../../adr/0004-import-uploads-into-the-instance.md))。

## 8. Python のモデルが遅いとき

optopus に組み込みの形が無い問題は、エージェントが Python で書きます。すると Result タブに
"This problem is written in Python, so every move runs through Python" というバナーと
**Port to Rust** ボタンが出ます。押すと、エージェントは同じモデルを Rust で書き、同じシードで
Python 版と照合し、一致すれば Rust に切り替えます。許容できる時間内に Python のモデルがこなせる
反復回数より、ずっと多くの探索が必要なときに効果があります。組み込みの問題はもともと Rust で
動いています。

## 頼み方のコツ

- **何を決めるか**、**何が良いか**(短い、安い、遅れが少ない)、**何を守るか**(容量、時間枠、
  先行関係)を書きます。コストを払えば破ってよい規則も伝えます。
- 気になる**規模**を伝えます。まず小さく始めてモデルを確かめ、それから大きくします。
- 何を**見たいか**を書きます。「トラックごとのルートを地図で」「機械ごとのガントチャートで」
  「遅れたジョブを一覧に」など。
- 1 つのメッセージで 1 つの変更にすると、リビジョンを比べやすくなります。
- エージェントにできるのは studio を通じた作業だけです。プロジェクトのファイルを書き、求解します。
  Web を見たり、添付したもの以外のあなたのファイルを読んだりはしません。
