# プロジェクト・リビジョン・ファイル

> この文書は[英語版](../../guide/projects.md)の翻訳です。食い違う場合は英語版が正です。

これらのファイルを自分で書く必要はありません。エージェントが書きます。それが何かを知っておくと、
**Model** タブを読んだり、変更を的確に頼んだり、結果を判断したりしやすくなります。

## プロジェクトとリビジョン

**プロジェクト**は 1 つの課題とその会話です。「配送ルートを計画する」「作業場の予定を組む」など。
エージェントが編集中のファイル、チャット、添付したファイル、そしてリビジョンを持ちます。

**リビジョン**は 1 回の求解です。エージェントがソルバーを実行するたびに、その時点のファイルが、
それが生んだもの(結果とビュー)と一緒に保存され、1、2、3… と番号が付きます。リビジョンは後から
変わらないので、いつでも戻ったり、比べたり、パッケージ化したりできます。データも持っているので、
新しいファイルを添付した後でも同じように解けます
([ADR 0004](../../adr/0004-import-uploads-into-the-instance.md))。

## ファイル

| ファイル | 中身 | 変更の頼み方の例 |
|---|---|---|
| `instance.json` | データ: 都市、ジョブ、品物、容量、取り込んだ行 | 「トラックを 4 台にして」「新しい需要のファイルを使って」 |
| `model.py` | 最適化問題: 何を決めるか、目的関数、制約 | 「配達の遅れのコストを 2 倍にして」 |
| `solve.json` | 探索の仕方: ヒューリスティック、そのパラメータ、停止条件、ラン数、シード | 「1 回 5 秒で 10 ラン回して」 |
| `view.py` | キャンバスに結果から何を描くか | 「機械ごとの空き時間を見せて」 |
| `rust/main.rs` | 任意: 高速化のために Rust へ移植したモデル | 「Rust に移植して」 |
| `app.json` | 任意: パッケージ化したアプリでその利用者が変えられるもの | 「利用者が注文データをアップロードできるアプリにして」 |
| `generate.py` | 任意: ベンチマーク用に、手元のデータに似たインスタンスをより多く作る | 「このようなインスタンスで探索を改善して」 |

`model.py` は、次の 3 つの方法のうち最初に合うもので問題を組み立てます。optopus の
**組み込みの問題**(TSP、配送計画、ジョブショップスケジューリングなど)、**`Formula`**(変数に対する
多項式の目的関数と制約。例えば品物ごとに入れる/入れないを表す変数)、そして **Python で書いた問題**
(それ以外すべて: 最大値、表の参照、シミュレーションなど)です。最初の 2 つは Rust で探索します。
3 つ目は手を 1 つ動かすたびに Python を呼ぶので、**Port to Rust** で速くなるのはこの場合です。

守るべき制約は、表現そのものに組み込まれる(巡回路はどの都市もちょうど 1 回訪れる)か、破っても決して
得にならないほど大きなペナルティになります。違反があればエージェントのビューが報告します。

ナップサックの例の `solve.json`:

```json
{
  "heuristic": {
    "kind": "SimulatedAnnealing",
    "neighbor": "Flip",
    "initial_temperature": 30.0,
    "cooling_rate": 0.999,
    "stop": {"max_iteration": 5000}
  },
  "runs": 3,
  "seed": 0
}
```

焼きなまし法を 3 ラン、それぞれ 5000 反復で停止し、シードを固定しているので同じファイルからは同じ
結果が出ます。ヒューリスティックを比べるときは `"heuristics"` にラベル付きで複数並べます
([`examples/workload/solve.json`](../../../examples/workload/solve.json) を参照)。

### 解から始める

`solve.json` で解を指定しない限り、各ランはランダムな解から始まります。
`"initial_solution": "plan"` と書くと、すべてのランが `instance.json` の `"plan"` から始まります。
解の形は結果に表示される形です。`model.py` の `encode_solution` がその形で書き出し、
`decode_solution` が読み戻します(workload の例に両方あります)。使いどころは次の 2 つです。

- **手元の案を評価する**: 現行のスケジュールなどを添付し、そこから始めるようエージェントに頼みます。
  各ランの初期値がその案の目的関数値になり、最良値との差が探索で改善できた分です。
- **前の結果から探索を続ける**(「リビジョン 3 の続きから」): エージェントがそのリビジョンの最良解を
  `instance.json` に写すので、新しいリビジョンは自分が何から始めたかを持っています
  ([ADR 0011](../../adr/0011-start-from-a-solution-in-the-instance.md))。

問題に合わない解(同じ都市を 2 度訪れる巡回路など)を指定すると、求解は start の段階で止まります。

## アルゴリズムを改善する

探索を良くするよう、あるいは決まった試行回数のあいだ自分で改善するよう、エージェントに頼めます:

> 探索を改善して。試行は 10 回、1 回の求解は 5 秒まで。

エージェントは 1 回の求解で変更を判断しません。それでは運や、1 つのインスタンスだけに合わせた
変更が得をするからです。まず**ベンチマーク**を作ります。いくつかの**学習用 (train)** インスタンスと
2〜3 個の**検証用 (validation)** インスタンスで、あなたのデータから、足りなければエージェントが書く
`generate.py` から作ります。そのうえでラウンドを重ねます。各ラウンドで種類の違う変更を 3〜4 個書き
(別のヒューリスティックや設定、速いか表現力の高い `model.py`、Rust への移植)、それぞれを、確かめる
仮説と一緒に**候補 (candidate)** として保存し、現在のリビジョンと**レース**させます。全員が学習用
インスタンスのすべてを同じシード・同じ 1 ランあたりの予算で解き(現在のリビジョンは 1 回だけ)、
対応のある検定が候補ごとに判定を出します
([ADR 0018](../../adr/0018-race-saved-candidates-against-the-incumbent.md))。studio がエージェントに
**採用 (adopt)** させるのは better と判定された候補だけです。現在のリビジョンの解を違う値に採点する
候補は、走らせる前に断られます。

| 判定 | 意味 |
|---|---|
| better | 有意に良く、どのインスタンスでも平均して 1% を超えて悪くならない |
| mixed | 全体では良いが、一部のインスタンスで明らかに悪い。採用しない |
| same | 有意な差がない |
| worse | 有意に悪い |
| rejected | 解の採点が変わっている: 探索ではなく問題を変えた |
| failed | 候補があるインスタンスを解けなかった |

ヒューリスティックの設定(温度、率、タブーの長さ、どの近傍を使うか)を調整するとき、エージェントは
設定を 1 つずつ評価しません。調整するパラメータとその範囲を指定すると、studio が irace と同じように、
抽出した設定を学習用インスタンスで**レース**させます。レースに残っている設定はすべて同じインスタンスと
シードで走り、数回走ったあとは Friedman 検定が明らかに劣る設定を外すので、ランはまだ優劣のつかない
設定に回ります。最良の設定は `solve.json` に書き込まれ、ほかの変更と同じく検証用インスタンスで
リビジョンと評価されます([ADR 0014](../../adr/0014-tune-settings-by-racing.md))。合いそうな
ヒューリスティックが複数あるときは、エージェントはそれぞれのパラメータごとすべてをレースさせ、
ヒューリスティックの種類もレースで選びます。勝ったものが `solve.json` の唯一のヒューリスティックに
なります。報告の最後には、設定では直せないことの**兆候**(signs)が出ます。最良の設定が範囲の端に
寄っている、設定がほとんど性能を左右しない、インスタンスごとに良い設定が違う、探索が早くに止まる、
受理される手がほとんどない・ほとんどすべて、といったものです。エージェントはこれを読んで次の変更を
選び、インスタンスごとに良い設定が違うときはそのことを伝えます。

エージェントは、変更を 1 つずつ詰めていく前に、探索の構造を根拠にもとづいて選びます
([ADR 0015](../../adr/0015-profile-heuristics-before-composing-them.md))。まず、あなたの問題を
文献での呼び名で言い表し、studio の**レシピ**を読みます。レシピには、その種類の問題で効くと報告されて
いる手法と、optopus にクラスのない手法を optopus のヒューリスティックの組み合わせで組み立てる方法
(反復局所探索、二段構成、VNS、マルチスタート、GRASP、メメティックアルゴリズム)が書いてあります。
次に、候補を 4〜6 個 `solve.json` に並べ、ベンチマークで**プロファイル**します。各候補はベンチマークの
ラン数と予算で学習用インスタンスのすべてを解き、プロファイルは次のことを示します。

- 順位と、勝ったインスタンス
- 予算の 10%・25%・50%・最後の時点で、その時点の最良が全体の最良からどれだけ離れているか
- 最良の解をどれだけ早く見つけたか

ここから、試す価値のある組み合わせを読み取ります。

- 序盤に先行する候補と最後に勝つ候補があれば、その 2 つの `Sequential`
- 早く止まる候補は、摂動を加える `Iterated` の中に入れる
- インスタンスごとに良いヒューリスティックが違うなら、1 回の実行の中で適応するもの

エージェントはそれらを variant として書き、単体で良かったヒューリスティックと一緒にレースさせます。
組み合わせの選択とその中の設定はレースが決めます。

チャット欄の **Web search** をオンにすると、エージェントは似た問題で報告されている手法を Web でも
検索します([ADR 0016](../../adr/0016-let-the-agent-search-the-web-when-allowed.md))。既定では
オフです。検索はツールの行として表示されます。読んだ内容は候補を示すだけで、すべての変更を判定する
のは引き続きベンチマークです。エージェントは出典を変更のメモに書きます。

better の変更だけが求解されて新しいリビジョンになります。それ以外は、エージェントが引き出した
教訓と一緒に台帳に残るので、同じ変更を二度試さず、まだ試していない種類の変更もわかります。キャンバスの
**Improve** タブで経過を追えます。ベンチマークのインスタンス、仮説、判定したすべての変更(判定、改善率、
求解されたリビジョン。行をクリックするとインスタンスごとの結果)、すべての調整とプロファイルが
並びます。最後にエージェントは、
どの選択にも使っていない検証用インスタンスで、最終リビジョンを出発点のリビジョンと評価し、そこでも
改善が保たれるときだけそれを示します。

ベンチマークには**テスト用 (test)** インスタンスも置けます。これは何の選択にも使われず、すべての
選択が済んだあとで、報告する結果を測るためだけに使われます。

評価の予算は各ヒューリスティック自身の停止条件を置き換えるので、長く走ることで勝つことはできません。
目的関数は比べる相手のリビジョンが決めます。そのモデルが候補の解を採点し直すので、ペナルティの重みの
変更は見抜かれます。何を最適化するかを変えるのはモデルの変更で、エージェントはまずあなたと合意します。
ベンチマーク、すべての評価・調整・プロファイルの記録はプロジェクトの `bench/` フォルダに残り、
プロジェクトと一緒にエクスポートされます([ADR 0013](../../adr/0013-improve-against-a-benchmark-of-instances.md))。

## 例

[`examples/`](../../../examples/) には 4 つの完成したプロジェクトがあり、テストがそれぞれを解いています。

| 例 | 問題 | 書き方 |
|---|---|---|
| `tsp` | 都市を回る最短の巡回路 | 組み込みの `Tsp`。Rust 移植あり |
| `job_shop` | 機械上のジョブをできるだけ早く終える | 組み込みのジョブショップスケジューリング |
| `knapsack` | 重量の上限内で価値を最大にする。`app.json` あり | `Formula` |
| `workload` | 作業を技能を持つ人に割り当て、最も忙しい人が最も早く終わるようにする。3 つのヒューリスティックを比較 | Python。Rust 移植あり |

これらは studio で開くプロジェクトではありません。試すには、その `instance.json` を **+** で添付し、
同じ課題を頼みます。例えば「この品物で容量 20 に価値が最大になるように詰めて」。例の `model.py` と
`view.py` を Model タブと見比べると、エージェントが書くものの感じがつかめます。

## プロジェクトの共有

ヘッダーの **Export** で、プロジェクトを zip としてダウンロードします。チャット、全リビジョン、
添付ファイルが入っています。受け取った人は **Import** で開き、新しいプロジェクトとして追加されます。
受け取った側のエージェントは、まず会話を読んでから新しいセッションを始めます
([ADR 0007](../../adr/0007-share-a-project-as-a-zip.md))。

## モデルをアプリにする

モデルが、エージェントと話さない人にも使える段階になったら、エージェントにアプリにするよう頼みます。
エージェントは `app.json` を書き、アプリの利用者が差し替えてよい表と変えてよい設定を定めます。
キャンバス上部の **Package** で、選んでいるリビジョンを zip としてダウンロードします。これは
エージェントもログインも無しで動きます。

```bash
uv run optopus-studio app optopus-app-<project>-r<rev>.zip   # http://127.0.0.1:8766
```

利用者は自分のファイルを渡し、値を設定して解きます。結果がおかしいときはケースをエクスポートして
あなたに送ります。そのケースを studio で **+** から添付すると、エージェントが再現します。この
リポジトリを持たない人に渡すときは、Docker イメージにビルドします。どちらも
[README](../../../README.md#packaging-a-model-as-an-app)(英語)に書かれています。
